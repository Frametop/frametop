# Frametop design

Why Frametop is built the way it is, and what we learned about SteamVR on the Steam Frame while building it. [reference.md](reference.md) describes the parts and how to run them. Read the SteamVR notes here before changing how the screens, the pointer, or the input relay talk to SteamVR.

## Goals

- Several desktop screens in SteamVR, each a real monitor with its own resolution and shape, placed anywhere around you.
- One physical mouse that drives a cursor through that 3D arrangement, and through the rest of SteamVR too: the dashboard, Steam, and other overlays.
- Controllers stay fully usable, and VR games aren't disturbed.
- Everything runs on the Frame itself, installed from a terminal on the headset.

## Screens

### Why our own compositor

SteamOS already shows a single-screen Plasma desktop in VR by running KWin nested inside gamescope. The first version of Frametop did the same with gamescope's `PerWindow` mode and `kwin --output-count N`, which gives each KWin output its own SteamVR overlay. It worked, but gamescope has two limits that ruled it out:

- It draws every window into one shared canvas of a single size, letterboxed, and never tells a window what size to be. So every screen had the same resolution and shape; portrait screens had to be rotated outputs on rolled panels.
- Its OpenVR backend allocates an upload buffer of exactly 1920 × 1080 × 4 bytes, so anything larger, such as 3440 × 1440, aborts it at start.

It also leaves the panels to SteamVR's dashboard, which places them and doesn't expose their position to other programs.

ft-screens replaces it. It's a small wlroots compositor that hosts the nested KWin. KWin's nested Wayland backend opens one window per output and resizes an output when the host configures its window, so ft-screens can give each screen any size, live. KWin needs `wl_compositor` v4 or later, `wl_shm`, `wl_seat`, `xdg_wm_base`, and `zwp_linux_dmabuf_v1` v4 with feedback from its host. KWin 6.6, which SteamOS build 20261009.6183636 ships, also refuses to start unless the host offers `wp_single_pixel_buffer_manager_v1`, `wp_viewporter`, `zwp_pointer_constraints_v1`, and `wp_presentation`. It draws each output's pixels on a synchronized subsurface and attaches a 1×1 single-pixel buffer to the toplevel, stretched to the output with viewporter. ft-screens presents the largest DMA-BUF in that tree, the toplevel's own included (KWin 6.2 draws there), and sends presentation feedback for the toplevel: KWin stops rendering after two frames without it. `xdg_toplevel_icon_manager_v1` and `zwp_keyboard_shortcuts_inhibit_manager_v1` stay optional. `scripts/update-check.py` fails when a newer KWin requires a host protocol this ft-screens binary does not name.

Frames go to SteamVR the same way gamescope sends them: OpenVR's `IVRIPCResourceManagerClient` imports each DMA-BUF (`ImportDmabuf`), and the overlay shows it as a `TextureType_SharedTextureHandle` texture. There's no copy and no size limit. The Frame's SteamVR supports this interface, but the OpenVR header bundled with SteamVR's samples predates it, so the build fetches a pinned header from Valve's openvr repository.

The small textures ft-screens draws itself (the controls, the hand glows, "grab that"'s halo, the carousel) go the same way, through `screens/overlaytex.cpp`: one linear DMA-BUF per distinct image, imported once and shared. Not `SetOverlayRaw`: the Frame's SteamVR never gives back the memory block each call takes, so a process's 201st call fails ("Refusing to create memory block because 201 blocks are already outstanding" in the journal) and the overlay keeps its old texture at its new size. That was the glow bug of 2026-10-15, after about 40 minutes of hand use. Other programs call it only a few times, or as a fallback.

Before settling on this, we tried KWin's screencast virtual outputs. KWin 6.2.5 crashed (`std::out_of_range` in `textureForOutput`) streaming one while nested in gamescope, and its headless backend doesn't implement virtual outputs at all.

A few wlroots details worth knowing: `wlr_shm_create` wants DRM format codes, not `wl_shm` ones, and KWin asks for server-side decorations before its first commit, when setting the mode would assert, so ft-screens answers on the first commit.

KWin 6.6 takes nested output scale from the host's `wp_fractional_scale_v1.preferred_scale`,
then applies it when an `xdg_toplevel.configure` resizes the output. `kscreen-doctor` alone
cannot change that scale. ft-screens advertises `wp_fractional_scale_manager_v1` and, once KWin has made a
`wp_fractional_scale_v1` object, sends preferred scale before logical dimensions, at startup
and when scale changes. Screen resolutions stay in pixels; configure dimensions divide them by
the scale rounded to 120ths. They also keep the resulting pixel dimensions divisible by the
whole buffer scale KWin 6.2 requires. KWin 6.2.5 makes no such object: it keeps the first
configure's pixels and the scale `kscreen-doctor` sets, and would make any later configure
that size times its scale, so there ft-screens configures a screen in pixels and never again
for a scale change, as before. ft-floatd sends spares' logical dimensions itself, after enabling and scaling them.
`kscreen-doctor` doesn't show that scale either: from 6.6 it reports a nested output's stored
scale setting, which stays 1. ft-layout sends ft-screens the layout's scales and never the
ones KWin reports, which would put a scaled screen back at 1, and positions screens by the
layout's scales too. ft-floatd and `ft-layout remote-view` also take screens' scales from the
layout (`kwin_scales` in `layout/ft_layout.py`), so a window floated off a screen at 200% floats
at 200%. KWin's support information (`qdbus6 org.kde.KWin /KWin supportInformation`) shows the
scale an output has.

### Placing and sizing

Because the overlays are ours, ft-screens places them exactly with `SetOverlayTransformAbsolute` and draws its own controls under each screen. OpenVR has no overlay-relative transforms, so the controls are repositioned whenever their screen moves.

The curved layout chains screens edge to edge, like monitors on a desk: the middle screen (or the seam between two) straight ahead, and each neighbour hinged at the previous screen's outer edge and turned to face you. An earlier version spaced screens by angle, which assumes every screen sits on the circle; a flat 3.6 m screen's edges are much farther away than its centre, so its neighbours landed in front of it. Solving for the hinge angle needs a scan and bisection, because a simple fixed-point iteration diverges for screens nearly as wide as twice their distance.

`SetOverlayCurvature` takes the fraction of a full cylinder that the overlay's width covers, so the radius is width / (2π × curvature). The stated width is the arc length, and the cylinder bends toward the viewer: at a 2 m radius, a 3.57 m wide screen's corners sit about 75 cm closer to you and 23 cm further in than a flat screen's would. Controls on a curved screen are placed on that cylinder, and the bar gets the same curvature.

A resize handle has to be able to shrink a screen from any direction, so the dragged corner follows the laser along the screen's diagonal rather than taking the larger of its horizontal and vertical reach. Pushing and pulling a carried screen moves it along the line from your head, because the 3D mouse's virtual controller sits just in front of the bar, below the screen's centre, so the line from the device points mostly upward.

Wherever ft-screens needs to know where a laser points (showing the controls, the resize tab, the roll knob), it uses the laser's own pose, the render model's `tip` component, rather than the controller's pose. On the Frame's controllers the tip points 40° below the pose's forward axis, so rays from the pose missed what the laser was actually on. The 3D mouse's virtual controller has no tip, and its laser runs along its pose. ft-screens reads the tip with `GetComponentState`: `GetComponentStateForDevicePath` without an input source handle fails for every component while a VR game runs, so in games the rays came from the pose, 40° too high.

`ComputeOverlayIntersection` ignores `SetOverlayIntersectionMask`, and a control can't be allowed to cover part of its screen, so the resize tab sits entirely outside the corner.

What SteamVR hits isn't the texture's shape but the mouse scale's: an overlay is as tall, for SteamVR's laser and `ComputeOverlayIntersection`, as its width times the mouse scale's height over its width, and the default scale is 1 × 1. With it, the grab bar (a 256 × 24 texture) took hits in a square as tall as the bar is wide, so it caught clicks meant for the bottom tenth or so of the screen above it. Measured with a 0.2 m wide 256 × 24 overlay: a hit area 199 mm tall at the default scale, 18 mm at 256 × 24 (the bar itself is 18.8 mm), and no change from an intersection mask. `MakeChrome` sets each control's mouse scale to its texture size.

`GRAB_BAR_PADDING_Y` (vertical) and `GRAB_BAR_PADDING_X` (horizontal), in Display Settings' Visibility & pins, add a fixed margin on each side of the visible drag bar: 0..50 centimetres, default 2. Target width is the visible width plus twice the horizontal padding; target height is the visible height plus twice the vertical padding. `screens/barhit.h` computes a padded texture with the pill kept at its original physical size. Raster sizes depend on each bar's width, and are capped at 1024 pixels per axis to bound memory for tiny bars with large padding. Up to eight CPU rasters are cached per settings version; equal rasters share an `overlaytex` image, and unchanged bars are not repainted every frame. No extra overlay is needed. The canvas also draws the optional preview's fill and outline, with separate colors, opacities and outline thickness. The row sits below the panel by a gap plus the larger of the target's and buttons' half-heights, and neighboring buttons sit beyond its expanded width. This prevents the enlarged target stealing content or button clicks, on flat, curved and pinned panels alike. Controller lasers and the 3D mouse use the same OpenVR intersection; hand-grab reach is independent. Settings are read at startup and `handsetting GRAB_BAR_... VALUE` applies them live. Always-visible previews keep only the bar up while its panel is visible; other buttons still fade, and hiding or pausing hides all controls. There is no multiplier setting.

The grab bar is the panel's menu (user, 2026-11-18, Option C: "a quick tap opens up the menu on the drag bar, and a hold and press acts as the current behavior"). A press on the bar waits before it moves the panel (user, 2026-11-19: "It should wait a second to half a second before actually moving the display when you grab it"): held 500 ms, the move starts, with a pulse on a controller; the laser moved 2 cm or turned 4 degrees sooner, or a wheel notch, and it starts then, so a quick swing isn't left behind. Either way it starts from where the panel is then, so nothing jumps. Let go before that and it was a tap: the menu opens and the panel never moved (`frametop.barmenu`, `screens/vrbarmenu.cpp`, rows in `screens/panelmenu.h`). While a press waits, or a move that began on the bar goes on, the release catcher follows that laser, so a release off the bar still ends it; one over the panel's content is the bar's, not the window's. The menu looks as the Option C design draws it (user, 2026-11-19: "Use that as the design"; `screens/barmenuart.h`, its layout `screens/menulayout.h`, its icons the design's own SVG paths through `screens/iconpath.h`): a #171d25 card, quick tiles on top (blue when on, white under a laser), rows with icons lit #3d4450 (Reset red), Placement and Bar Position showing their value with a chevron, a blue check on the choice picked under a grey caption, and the bar blue while its menu is open. The reset question is Steam's dialog: a title, a line on what happens, and Cancel (the focus) and Reset. The device's own movement decides, not the panel's, since a 1 degree wobble moves a panel 2 m out 3.5 cm. A finger's poke on the bar opens it too; a pinch or a grab on it still moves the panel. While it's open, hand input leaves its panel to it: a fingertip through a row presses it, one through the panel beside it closes it, and the panel stays out of hand input until that fingertip is back out in front of its surface (2 cm, measured on the curve of a curved panel) or 5 cm off its edges, 3 seconds at most, so the same poke doesn't click what's under the row. Everything the round buttons did is a tile or a row: the tiles Curved, Rotate (held: the roll; clicked: level), To Desktop and Close (floating windows); Placement's page (In the Room, Keep in View, On Dashboard, Stay Shown), View in Theater, Move All Screens (held: the layout's carry), Bar Position and Reset Layout, which asks before it does. So a pooled control set is two overlays, the bar and the resize corner, not ten, and the menu is one overlay for every panel. A right click on the bar opens the menu at its edges page: the four edges the bar can sit on, Bottom (the default), Top, Left or Right. On a side the bar stands on end, flat even on a curved panel (an overlay bends along its own width). The row's geometry is `screens/barside.h`'s, so the controls, the reveal zone, the aim box and the hand targets all follow the same edge. The resize tab stays at the corners. The row sits inside the panel's edge, over its content while it shows (user, 2026-11-18: "the overlay should be inside of the display"): hung outside, a bar between two stacked tiles was hard to grab. It still shows only when a laser, the 3D mouse or a hand comes near, and a set's overlays go back to the pool once they fade, so nothing invisible takes clicks meant for the content. For hands, a control now wins over the content under it, for pokes and button pinches alike. The menu opens over the panel beside the bar, where it was clicked, toward the panel's middle, and so does the reset question: past the edge the panel's plane runs on behind the next tile, because the tiles curve round the head, and that hid a menu there (tested 2026-11-18). Each panel's edge is remembered by its tile key (`screen:N`, `app:ID`, `remote:HOST/APP`) in `~/.config/frametop-bars.txt`; `barside <screen> bottom|top|left|right|menu` sets it or opens the menu from a script.

### When SteamVR loses the room

Every screen sits in SteamVR's standing space, so it stays put in the room only while standing does. When the Frame loses tracking, vrserver switches to its dummy universe (424242) and, once tracking is back in a new tracking world without relocalizing, to a new universe with a guessed floor ("default floor height without bounds": standing at (0, 1.6, 0), yaw 0, in `~/.config/openvr/config/chaperone_info.vrchap`). When it relocalizes, it restores the saved room, and standing jumps: vrserver logged three such restores on 2026-10-27 and 2026-10-28, and with the room's floor about 1.07 m under raw tracking's origin on this Frame, a guessed 1.6 m floor puts standing about 0.5 m off. Screens placed while the temporary universe was in use (the desktop starting, a reset, a carry) jumped with it, mostly up. The SteamVR dashboard doesn't show it, because it's placed in front of you each time it opens.

So ft-screens remembers, for each screen, the universe it was placed in (`screens/universefix.h`). It reads the HMD's `Prop_CurrentUniverseId_Uint64` every tick (a cached read: about 0.1 µs), and when it changes, the screens placed in the universe it left move by standing's jump, if that one was temporary, so they stay where you saw them. The jump is the head's: standing changes in one tick while the head hardly moves, so it's the one head step around the switch, within three ticks either side, that the head's own motion (the median step there) doesn't explain, turned about the vertical only. Screens placed in the room stay put, since the restore puts the room back where they were in it. A recenter keeps the universe, so screens follow a recenter as before. The front slot's home and parked remote displays follow with their screens. A universe the file doesn't list counts as a room, which leaves things as they were before the fix.

`ft-layout capture` and `save` ask ft-screens' `universe` first and refuse in a temporary universe: a layout is saved relative to the head, and in a temporary universe the screens placed in the room aren't where they are from it.

ft-screens' tracking watch (`screens/trackwatch.h`) logs standing and chaperone events, raw->standing moves, universe changes, and head jumps in standing, with wall-clock times to line up with `vrserver.txt`, and the fix logs each switch it handles (`universe A (temporary) -> B (room): standing jumped ...; moved screen(s) ...`). The log is `~/.local/state/frametop/screens.log`, kept across desktop starts and reboots and rotated at 8 MB (`screens.log.1`, `.2`). It was `/tmp/frametop-screens.log`, which is in RAM and was emptied at every desktop start.

### Pinning

Pinning started as "bring the screen to your wrist", which doesn't work for big screens, because their centre is far from the edge you bring close. It became aiming: while a screen is carried, the line from the carrying device to its bar is tested against the other hand controllers. Crossing a controller's 6 cm ring arms the pin (leaving past 9 cm, so it doesn't flicker), and crossing it again disarms it. The pin happens on release, with the screen's pose at that moment, so you can arm it and then turn the screen. An earlier version pinned the moment the laser touched the wrist, which left the screen at whatever angle the carrying hand had while pointing there.

A pinned screen's alpha follows the angle between its front and the direction to your head, fully visible inside the wrist angle and fading over the last 10°.

A head pin is the same pin on the headset (device index 0): the screen's transform is relative to the headset, so SteamVR keeps it rigidly in your view with no lag from us. It skips the facing rule, since a screen on your head always faces you the way it did when pinned. There's no aiming gesture for it: the line from the carrying device can't sensibly pass through your own head, and a ring in front of your face would be in the way. So it's set from Frametop Display Settings or `ft-layout`, and it pins the screen where it is. Carrying a head-pinned screen re-pins it on release, like a wrist pin, so it can be adjusted in VR.

A level head pin (`SCREEN_PIN_LEVEL=1`, "Pin only follows horizontal movement" in Display Settings) follows the head turning and walking, but not looking up or down, tilting, or crouching. SteamVR can only pin an overlay rigidly to a device, so a level pin is an overlay in the room that ft-screens moves every tick: its frame is on the floor under the head, turned with the head's forward laid flat (tilting doesn't change it; looking up or down only shortens it, and near straight up or down a little of the right vector takes over smoothly: `screens/levelpin.h`), and the pin's offset holds the height. The head pose is predicted for when the next frame shows (vsync to photons), since SteamVR moves device-pinned overlays with its own prediction and an unpredicted one trails a turn. It moves only shown level pins, and only when the frame moved by 0.2 mm or about 0.003 degrees, so a still head costs nothing; a turning head costs one pose read and about ten transform calls per pinned screen per tick. Outside ft-screens it's still a head pin: `get` reports it relative to the headset and `pin N head REL` takes it so, so profiles keep working either way, and switching the setting changes existing head pins over where they are. A walking head pin (`SCREEN_PIN_LEVEL=2`, "Pin follows walking only, not turning") is moved the same way on a frame with the room's axes under the head (`levelpin::WalkFrame`): only the head's floor position counts, so the screen keeps its height and its facing in the room while you walk, and turning, looking or crouching leave it where it is. Display Settings sends it as `handsetting SCREEN_PIN_LEVEL 2`.

A dashboard pin (`pin N dashboard`, "On the dashboard" in Frametop Settings) keeps a screen's place relative to the SteamVR dashboard: drag the dashboard, or close it and open it again (it reopens in front of you), and the screen goes with it, turn and tilt included. OpenVR can't parent an overlay to another one here, and it won't let another process read the dashboard's own transform: `valve.steam.gamepadui.main` is a `DashboardTab` overlay, and `GetOverlayTransformAbsolute` on it fails with `WrongTransformType` (so do the thumbnails, `Subview` layers and the keyboard). Steam's bar under the dashboard, `valve.steam.gamepadui.bar`, is an `Absolute` overlay that Steam places rigidly with it, readable from any client: a probe on the Frame (2026-11-16) logged it at about 90 Hz through opens, drags and closes, and a marker placed from it every tick followed the dashboard. So ft-screens reads the bar every tick and moves dashboard pins itself, as it moves level pins, whenever the bar moved. Steam draws the bar scaled (its axes about 0.369 long on SteamOS 0.4.5), so the scale is taken out first: the frame is the bar's position and turn. Only some reads count (`screens/dashanchor.h`): the bar shown, the pose finite, a rotation at one scale and not the identity (a hidden bar reports the identity), and from the second shown read in a row, since on the first frame after an open the probe saw a `nan` and stale poses on panels beside it. While the dashboard is closed the last good frame stays, so the screens stay where they were; whether they show then is the visibility mode's business (Only with the SteamVR dashboard open hides them with it). Dashboard pins are moved hidden too, so one that shows with the dashboard is in its new place when it does. They skip the facing rule, like head pins. The dashboard isn't seen until it first opens in a run, so a screen pinned before then stays in the room until it does, then goes on it where it is (or where a saved pin puts it). `get` reports the pin as the bar's frame to the screen, so profiles keep it. `system.systemui` and `valve.steam.gamepadui.floatingfooter` also follow the dashboard, but the first jumps on opens and the second is the bar plus 2 cm, so the bar is the one. It's a Steam-internal name: `scripts/update-check.py` warns when Steam's UI is up without it.

### Dashboard tiles

Any panel can be anchored to the SteamVR dashboard on its own: a desktop screen, a floating window, a remote display, or a gamescope app. On Dashboard under Placement in its bar's menu anchors it (In the Room or Keep in View there takes it off), and Stay Shown (while anchored) toggles whether it stays shown with the dashboard closed. A laser's click or a finger's tap picks them. Anchored panels stay shown with the dashboard closed as `DASH_TILE_STAY` says, on unless set (user, 2026-11-18: SteamVR closes the dashboard at a click in the room, and the panels went with it), except one Stay Shown set the other way; Stay Shown back to the setting's way follows the setting again. Tile memory keeps that as STAY 0 (as the setting says), 1 (stays) or 2 (hides); an older memory's 0 now follows the setting. Steam's own window never stays: Steam paints it only while its tab shows. Anchored panels stand round you like a desk of monitors of different sizes (user, 2026-11-17: a command wall that handles displays of different heights, orientations and aspect ratios, "Monitor desk"). Each panel has a natural size, its pixels at `DASH_TILE_PX_PER_DEG` (48) a degree, so text is the same size on all of them, times its own scale (`Meta+Ctrl+arrows`, a quarter to six times; no cap, the user's call). They go in columns as in Hyprland's scrolling layout, a new one right of the focused one. The columns pack as close as their panels allow (user, 2026-11-17: "as minimal space between the monitors as possible"): a column comes in until each of its panels is a gap from every panel left of it that it shares some height with, so a wide or tall panel high up in one column doesn't hold a short neighbour away at the desk, and a short one can sit under a wide one's overhang. A column's narrower panels lean against one edge of its widest panel: the side that lets the strip pack narrowest (a short neighbour tucks under the other side), or else the side toward the strip's middle, so the room left under a wide panel ends up at the strip's outside rather than between monitors (user, 2026-11-17, after a test with a tall app beside an ultrawide over Steam). A column stands on the desk line, `DASH_TILE_DESK_DEG` (12 degrees below your eyes), its panels stacked upwards from it, so a tall portrait screen just stands taller than its neighbours and the top edge is ragged. A column is as wide as its widest panel, and narrower ones share a shelf in it, side by side, while the shelf, gaps and all, is no wider than that, the first from the desk up on the left; a shelf is as tall as its tallest (user, 2026-11-19: "if we had one window that was 1,200 pixels across, you could fit two windows that are 500 pixels across above it ... a column is defined by its widest screen"). Once the strip is `DASH_TILE_WALL_DEG` wide (120 degrees), a new panel goes on top of a column no narrower than it, with room for it under 50 degrees tall as your eyes see it: where it adds the least height (beside others on the top shelf), then the lowest, then the one nearer in front; else in a column of its own (user, 2026-11-19: twelve PC windows opened at once stacked on whatever column was lowest, and a wide screen in a column of narrow windows left "a massive gap in the middle"). A panel that isn't shown (no picture yet, hidden on its own, or Steam's window with the dashboard closed) is laid out at no size, so its neighbours close up. Reset Layout packs every tile again the same way, widest first, the widest column in the middle and the rest alternately right and left of it, and gives each panel not shown a column of its own at an end (`screens/tilepack.h`). A column has a base row on the desk line: the panels before it stand above it and the ones after it hang under the line (user, 2026-11-19: "displays go from the center row down or up"). Meta+Down on the base hangs it under the panel above, Meta+Up brings it back, and a drop below the desk line hangs the panel there. Reset Layout shares a column's shelves round the line: the first on it, then one above, one under, and so on. A shelf narrower than its column leans against the side you put it on: Meta+Left/Right moves it to that edge before taking it to the next column, and a drop leans it toward the side of the column it was let go on. `DASH_TILE_FIT=1` swaps the columns for a fitted layout (`screens/tilefit.h`): largest first, each panel goes beside, over or under one already placed, wherever the layout's box stays narrowest plus 1.6 times its height, with the largest on the desk line in the middle. Every panel faces you round the head where the dashboard opened, its corners on a sphere (`DASH_TILE_RADIUS`, 2.7 m), not its middle: neighbours' corners meet at the same depth whatever their widths, and a wider one comes nearer. Tiles keep `DASH_TILE_GAP_DEG` (0.8 degrees, about 4 cm) between them, round you and up. When the strip would pass 360 degrees or a column would reach past 80 degrees up, every panel shrinks by the same factor, so nothing piles up at the pole. A tiled panel is flat, as the tiling's sums take it: a curved one would reach past its column into its neighbour. Its own curve comes back when it leaves the tiles. Steam's menu is part of the strip whenever the strip would reach it: the Steam button opens it in front, the palm menu off to the side. A slot as wide as Steam's bar is kept clear where it is, with the strip's columns either side of it. The grid keeps a split for each place the menu opens: in front (the Steam button, within 45 degrees), off to the right and off to the left (the palm menu). Each is chosen the first time the strip reaches the menu there, so the strip's middle is nearest in front of you, and the slot stays where it is in the strip: a new panel goes on its focused neighbour's side (with none tiled, the end that brings the strip's middle nearer in front as shown), a drop on the side you let go, and Meta+Left/Right steps a panel across the slot shown. Opening the palm menu leaves the front split as it was. A split you set, by taking a tiled panel across the menu with a drop or Meta+Left/Right, is never replaced. One only chosen for you is chosen again when the dashboard opens and a fresh choice puts the strip's middle more than 30 degrees nearer in front (new panels all went one side, or some went), both with the menu where it opens now and where it opened the time before. So a menu that opens in one place, then another and back doesn't move panels across it, and one that has moved for good is followed from the second open there. Splits count columns, so swapping two columns round one place's menu can move them across another place's. Until the strip centred in front of you reaches the menu, there is no slot and the strip stays centred; once it does, the slot stays for that open. Emptying the grid clears the splits. `screens/tiling.h` places the columns, `screens/tilegrid.h` keeps the grid and its moves, `screens/slotsplit.h` picks the split round Steam's menu, and `screens/dashtiles.h` holds what's anchored, the satellites, and each app's memory. `screens/vrtiles.cpp` is the OpenVR side: the group frame, the pins, the focus border, the memory file and the `tiles` commands.

By default the wall stands at Steam's bar (`DASH_TILE_AT_BAR`, on unless `0`; user, 2026-11-18: "the same distance that the Steam menu is ... the middle display should be positioned right above where the Steam menu bar is"). When the dashboard opens, the group faces the bar from your head, so the strip is centred over it. The wall's radius is the bar's distance from your head plus 0.3 m (user, 2026-11-18: "move the display's distance a little bit back ... I can't interact with the Steam menu because it's covered by one of the displays"): a flat tile's middle is nearer than its corners and the laser starts at your hand, below your head, so at the bar's own distance the lowest tile stood between hand and bar. The desk line is 4 degrees above the bar's top edge (`kOverBarDeg`; at the tiles' 0.8-degree gap the bar, which draws over the tiles, covered the front tile's bottom edge: user, 2026-11-18, "rise that up just a little bit") (its height is its width at its mouse scale's shape, 1800 x 120, since it has no texture of its own). `DASH_TILE_RADIUS` and `DASH_TILE_DESK_DEG` apply only with it off. Steam's page stands over the bar at the bar's distance, just in front of the wall, so without `STEAM_DASH_PANEL` the slot kept for it is as wide as the page (its overlay's width at the bar's scale), not just the bar. The group rides on the bar's frame like every dashboard pin, so dragging the dashboard by its bar carries the whole layout. With `STEAM_DASH_PANEL` on, the strip is turned so Steam's tiled page stands over the bar, as Steam's own page would, rather than the strip's middle (`Board::Recentre`); its window is tiled only after the dashboard first opens, so the group is placed again then. `screens/dashtiles.h`'s `AtBar` does the sums.

`tiling::Arrange` always lays the strip out centred, so with no slot kept the `Board` turns it after a change to keep the panels where they were (`Board::Pan`; user, 2026-11-18: a monitor moved from the right to the left was centred and every other one pushed right, "it should put that monitor roughly where I put it, but not shift all monitors around"). The turn is the median of what the other columns want to stay where they were, each voting by its widest panel (which leans against nothing), so most columns stay exactly put. A mean let one odd panel pull the rest (a column's narrower panels can flip the way they lean, and a narrow one left alone by the wide one it leaned on lands somewhere new), and a vote a panel let a stacked column outvote the one across from it. Moved to an end, the others stay put; moved between two, both sides make room by half its width. The moved one counts only when it's alone (then it goes where it was let go). The turn never takes the strip off straight ahead: it always reaches the bar, or where you faced. Opening the dashboard centres it again (over the bar, or Steam's page over it). With a slot kept for Steam's menu, the layout is placed round the slot instead, as before.

The group follows the dashboard the way dashboard pins do (Pinning, above): each tile is pinned rigidly to the bar's frame, and each time the dashboard opens a new group frame is taken round the head, facing the way you face, wherever Steam put its bar. Looking steeply up or down, the headset's up joins its forward to give the way you face. The visibility mode (Visibility & pins) is the room's panels' alone: anchored panels show with the dashboard, or always when they stay. With the pointer or your gaze on an anchored panel, `Meta+arrows` move it between columns and within its column, and `Meta+Ctrl+arrows` make it about 10% bigger or smaller a step (Right and Up bigger). The relay hands those keys to ft-screens only while ft-screens says a tile has the focus (`tilefocus`), so otherwise they reach Plasma. The tiles never change a window's pixels, only its size in the room, so a floating window or an app keeps its resolution and its text grows with it. With Steam's own window on a tile (`STEAM_DASH_PANEL`), Steam's menu has no tile of its own: it's glued flush left of that tile (`screens/steamglue.h`), cropped to the strip Steam draws (its page reports that over DevTools, every 20 ms while the laser is on it, so the crop follows its labels opening leftwards), at the same density. Steam snaps its labels open about 0.5 s after the laser arrives and shut about 0.8 s after it leaves (its own hover delays, measured 2026-11-18), so the crop slides to each new size in 180 ms rather than jumping, and slides shut only once Steam has shut its labels, so the icons are back in the strip before it closes in on them (user, 2026-11-18: shut at once, it showed the blank end of the labels until Steam drew the icons), or 2.5 s after the laser left at most (`steamglue::Goal`, `steamglue::Slide`), and moved, shown and tiled with it. The tile counts the strip's closed width, so opening the labels doesn't move the tiles; open, they go over the next tile left. Dragging a tile drops it where it lands in the grid. Pulled well away, it tears off as a satellite: still anchored, at its own place relative to the group. Each app (`app:` and its desktop file for a floating window, `steam:` and its app id or `x11:` and its class for a gamescope app), screen and remote display remembers its last state in `~/.config/frametop-tiles.txt`, a PC window's under its app (`remote:HOST/app:APP`, from desktopless mode's `key=APP`). A window (a floating Frame window or a PC window) goes on the tiles when it comes unless its app was put In the Room from its bar's Placement menu, remembered as `room` (user, 2026-11-19); screens and remote displays stay where they are until anchored. The memory is written 2 seconds after a change (a burst is one write, off the frame it came in) and when ft-screens stops, and profiles keep the grid ([profiles.md](profiles.md)). A profile puts its tiles back with `tiles set` and `tiles add` chunks sent at once; an add more than 5 seconds after the last set or add is one of its own, after the tiles already there.

Yoshey's [dashboard-anchor branch](https://github.com/Yoshey/frametop-dashboardanchor/tree/dashboard-anchor) came first: an anchor per display, following the dashboard. Its commit is in the history under his name, and the tiles grew from it.

### Named layouts

Named layouts are now profiles, which also hold which screens are hidden and which apps to open, with where their windows go. See [profiles.md](profiles.md).

A profile's screen part is the custom arrangement under a name: each screen's pose relative to your head, width, curve, and pin, but not its resolution or scale, which need a desktop restart or belong to KWin. Using one copies it into the custom arrangement, so everything that applies the layout (desktop start, Meta+Shift+R, Arrange now) works unchanged, and `active` remembers which name it came from. Saving without a name (`ft-layout capture`) clears `active`, because the screens have been placed by hand since. Layouts are kept per screen number, so one saved with a different screen count still applies: missing screens keep their last saved place or the preset's.

### Visibility and VR games

`VROverlayFlags_MakeOverlaysInteractiveIfVisible` keeps SteamVR's laser mouse on while an overlay with that flag is visible. Without it, the laser is off whenever the dashboard is closed: the first click on a panel only turns it on, and the laser turns off again as soon as it leaves every panel. With it, controllers work the screens normally, but the laser also takes the controllers away from a VR game.

`IVRApplications::GetCurrentSceneProcessId()` is 0 when no game is running (the Frame's home environment isn't a scene app) and the game's process ID while one is. ft-screens checks it twice a second, turns the flag off while a game runs, and by default hides the screens unless the dashboard is open. Flatscreen games run inside Steam's gamescope overlay and aren't scene apps, which is why "only with the dashboard open" is offered as a controller setting.

In a game, Frametop's panels work like SteamVR's own floating windows: point a controller at one and its laser comes on, point away and the game has the controllers again. ft-screens turns the flag on for a panel while a hand controller's laser pose meets it, its controls, or a floating window's popups. It finds that from the poses it already reads to show the controls, so SteamVR's laser doesn't have to be on first. Leaving takes a margin two control-sizes wide and 0.3 s, a drag or a held button keeps the flag on, and the keyboard, a single overlay, uses SteamVR's `ComputeOverlayIntersection`. The 3D mouse doesn't need any of this: it has its own laser mode.

## Floating windows

[floating-windows.md](floating-windows.md) describes the feature and its parts. Drag and drop and the clipboard only work between windows of one compositor, so a floating window stays a KWin window and gets a KWin output of its own: one of the spare outputs KWin opens after the screens, shown by ft-screens as a panel cropped to the window. What follows is how KWin 6.2.5 behaves underneath that, from its source (`src/backends/wayland/`) and from trying it on the Frametop desktop.

### KWin's nested outputs

- Disabling a nested output keeps its host window. `Output::applyChanges` only flips `enabled`, KWin stops rendering it (no more commits), and Plasma drops its desktop view. So ft-screens keeps the same toplevel, and its screen numbers stay put. Enabling the output again resumes on the same toplevel.
- Each output's host window is titled `KDE Wayland Compositor WL-<n>`, with `- Output disabled` appended while it's disabled (`WaylandOutput::updateWindowTitle`, on every `enabledChanged`). ft-screens reads the title to tell screens (`WL-0` to `WL-<SCREENS-1>`) from spares, and to see a spare turn on and off.
- A spare resized while it's disabled comes up at the new size on its first frame, so floating a window needn't blink. Outputs with gaps between them are accepted, so ft-floatd places spares apart from the screens and from each other: a grid below them, 4000 logical pixels a cell. Xwayland's coordinates are the layout's times its largest output scale, and they wrap past 32767, so an X11 window on a spare past that took no clicks (Brave on the 4th spare at x 27000 and scale 1.25 sat at x -31506; KWin still focused it). The grid ends at 20000 for 16 spares, within the limit up to scale 1.6.
- KWin keeps a Wayland popup inside its parent's output (`XdgPopupWindow::updateRelativePlacement` uses the output's placement area), and X11 apps place their menus within the monitor. That's why a floating window's output has a margin around the window: menus and dropdowns open past the window's edges, into the margin.
- KWin makes a nested output the size it's configured to times its scale, rounded (at 1.5 it lays out 1067 × 667 on a 1600 × 1000 buffer), and gives the buffer a whole buffer scale (1.2 becomes 2). A buffer whose size isn't a multiple of that is a protocol error that disconnects KWin, so ft-floatd sizes spares in multiples of it. After a scale change, ft-floatd asks for the output's size again in the new scale's terms, or the next configure would make it the old size times the scale.
- **Virtual outputs don't work.** `createVirtualOutput` makes an output window but never adds it to the backend's `m_outputs`, so `findOutput()` returns null when the pointer enters it, and the next line dereferences it (`Q_ASSERT` is compiled out). A click on such a panel would crash KWin. This rules out virtual outputs (`stream_virtual_output`) for floating windows without a patched KWin.

### The pointer

- Pointer positions reach KWin only through motion events: the output's position in the layout plus the position on its window. When ft-screens stops sending motion, KWin's pointer stays put.
- KWin starts an interactive move on the press itself, before any motion. So ft-screens stops sending motion as soon as a press lands in a floating window's title bar (from the frame and client rectangles ft-floatd sends it), with no round trip, and carries the panel instead. KWin gets the release at the press point, and the window moves by nothing on its output.
- KWin's nested backend ignores the position in `wl_pointer.enter`, and wlroots drops a motion to the position it entered at, so the first click after crossing onto another panel landed where KWin's pointer had been. ft-screens enters one unit off.

### The KWin script

The KWin side is a script (`float/frametop-float.js`), not a C++ effect, because a script keeps working across KWin updates and an effect would have to match the host's exact KWin build. KWin scripts can call D-Bus but can't serve it, so ft-floatd's commands come back through a long poll: the script calls `NextCommand`, which answers when a command is ready, or empty after 20 seconds, under KWin's 25-second D-Bus timeout. If no reply comes within 30 seconds, a watchdog calls again, and waits twice as long each time until a reply comes (up to 5 minutes). The 30 seconds have to stay above KWin's timeout, or a late reply would start a second poll. A few things about KWin's script engine:

- `windowAdded` reports popups as windows of their own (`popupWindow` true, `transient` true) with their geometry.
- Setting `frameGeometry` applies asynchronously: the app has to answer the new size first.
- A script can't read a window's maximize mode, so the script counts a window as maximized when it fills its output's maximize area.
- `globalThis` isn't defined. `print` goes to the journal unless `QT_FORCE_STDERR_LOGGING=1`.
- `callDBus` never calls back when a call fails (an error reply, the name gone from the bus, or the 25-second timeout). KWin only logs `Received D-Bus message is error`, so a script that waits for the callback waits forever.

The title bar's float button is Frametop's own window decoration (`decoration/`), written in QML for KWin's Aurorae engine, which loads it without compiling. A C++ fork of Breeze would have to match SteamOS's exact KDecoration build. A decoration can only make the window requests KWin offers it, so the button toggles keep-below, which has no visible effect on a window alone on its own output, and the script treats keep-below as the floating flag.

### KWin's placement memory

KWin keeps each window's geometry, full screen, and maximized state for each layout of the outputs (its `PlacementTracker`, keyed by every enabled output's name and geometry). When the outputs come back to a layout it has seen, it puts every window back as it was in it. That's for plugging monitors in and out, and it does harm here. A spare output changes size after its window does, so what KWin keeps for a spare's size is the window's next size. Resizing a floating window back to an earlier size made the window and its output flip between two sizes for good (Dolphin went between 1187 and 1424 logical pixels wide, its output between 1687 and 1925). Full screen flipped the same way, and floating or docking one window could move others, even onto a spare or off one.

So the KWin script keeps where each window belongs: where ft-floatd put it, or where it went outside an output change. While KWin changes the outputs, it reports nothing to ft-floatd. Once KWin is done (`screensChanged` comes after its restore), it puts floating windows back, and the screens' windows too when only spares changed. KWin's resize request hasn't reached the app by then, so the app never sees it. A size asked for is held for a second, since an app can still answer an older request, and then the script takes the size the window has. If `screensChanged` doesn't come within 2 seconds, the script stops waiting for it.

KWin also ends an interactive move or resize whenever the outputs change. So during a resize by a floating window's edge, ft-floatd only crops the panel to the window, and resizes the output when the drag ends. The margin is the room to grow until then.

## Gamescope apps

Flatscreen apps started from the SteamVR dashboard run in Steam's own gamescope session, outside KWin, and gamescope shows each one on a dashboard panel of its own. ft-screens makes them Frametop panels instead, with a panel's controls, the dashboard tiles and the 3D mouse (`GSAPP_PANELS`, Dashboard apps in Display Settings; on by default). gamescope's SteamVR backend can forward an X11 window's frames to an overlay someone else made: the window's `STEAM_GAMESCOPE_VROVERLAY_TARGET` property names the overlay, and the overlay names gamescope its renderer (`SetOverlayRenderingPid`, the pid in the root window's `GAMESCOPE_PID`), since only its creator or renderer may set its texture. The frames go over as DMA-BUFs at the window's own size, with no copy. So ft-screens watches gamescope's app display, gives each app window a panel, and tags it as it's created: a window that maps untagged gets gamescope's panel for a moment, and the dashboard opens for it. A window that unmaps keeps its panel, hidden, and its tag for 5 seconds, so one that maps again comes straight back in its place. The app display is `:1` on the Frame today, with Steam on `:0`, but gamescope picks them as it starts. `screens/gsdisplay.h` lists the ones to try: `GSAPP_DISPLAY` alone when it's set; else the one in Steam's `STEAM_GAME_DISPLAY_0`, every socket in `/tmp/.X11-unix`, then `:1`. The first that forwards windows and isn't gamescope's first Xwayland (`GAMESCOPE_XWAYLAND_SERVER_ID` 0, Steam's own) is it. ft-screens' container can't read Steam's environment, so there it's the sockets that find it. Menus, tooltips and dialogs get overlays of their own over their app's panel, where the app put them. The first time an app is seen its panel is anchored to the dashboard, staying shown; after that it comes back as it was. Off, every window goes back to gamescope.

Input: the laser's pointer, buttons and wheel go through XTest. On gamescope's Xwayland that goes through gamescope's own input socket (`LIBEI_SOCKET`) to the window gamescope focused last. That reaches a tagged window only if it had gamescope's focus before it was tagged: gamescope drops a tagged window from its focus list, and ft-screens tags each window as it's made, before it maps, so a window that never had focus got no pointer at all (Slay the Spire 2's clicks did nothing, 2026-11-18; the Konsole of the spike worked only because it had focus first). So when the laser first comes onto an app panel, and on a press on another one, ft-screens hands that window gamescope's focus: it takes the tag off, waits until `GAMESCOPE_FOCUSED_WINDOW` on the root of gamescope's first Xwayland (`:0`, server id 0, the same `GAMESCOPE_PID`) names the window, and tags it again (`Link::FocusSaying`, `screens/gsforward.cpp`; 8 to 14 ms on the Frame, at most 250 ms). The pointer stays with it after. Untagged for seconds instead, gamescope gives the window a `valve.steam.desktopgame.<appid>` overlay of its own and SteamVR takes it for a theater game, so the wait is kept short. `screens.log` says how each handoff went (`gamescope apps: gamescope's focus to window ...`). Keys don't follow: gamescope drops a tagged window from its focus list, and its keyboard focus is where XTest's keys and every libei client's land. So a click on an app gives it the typing, the relay grabs the keyboards as it does for the desktop, and keys go straight to the window as synthetic events until a click on another panel. Most apps take those (Slay the Spire 2 does: Escape closed its Settings, 2026-11-18); ones that refuse synthetic events (xterm by default, games that read raw input) don't type. GTK3 apps ignore them too: GTK3 reads keys through XInput2, and synthetic events come only as core ones. Starting one with `GDK_CORE_DEVICE_EVENTS=1` (in Steam, its launch options: `GDK_CORE_DEVICE_EVENTS=1 %command%`) makes it read core events, and it types (tested on Xvfb with GTK 3.24, 2026-11-16). Full Keyboard types through gamescope's libei, so it doesn't reach them either.

View in Theater: a Steam game's panel has a theater button left of its bar, in the slot a floating window uses for its back-to-the-desktop button (the anchor moves in next to it), and a fifth row in its grab bar menu (`screens/vrbarmenu.cpp`), as Steam's tile does (the user's pick, 2026-11-18: hand theater to SteamVR; in the headset the menu row alone went unfound). The laser, the 3D mouse and a hand press all work it. It's also how a game gets the controllers as a gamepad: in SteamVR's theater Steam Input sends the pad to the game, so a game's panel has no gamepad pill (user, 2026-11-18). ft-screens hides the panel and takes the tag off the game's windows (`Control::Lend`, `screens/gscontrol.h`), so gamescope gives the game its own `valve.steam.desktopgame.<appid>` overlay and SteamVR a frame for it, and sends `gametheater <appid>` to ft-dashpatch, which waits up to 3 s for that frame and calls its `docking.SetInTheater()`, as SteamVR's own button does (`pointer/dashpatch/gametheater.py`). SteamVR put the frame in its theater by itself only sometimes: with the dashboard open it docked it there instead (testbench, 2026-11-18). In the theater the game takes the laser and keys from SteamVR, and SteamVR's strip under it has Show Keyboard, Return to Dashboard, More Options and Exit Game. ft-dashpatch reports which game the theater shows (`steamvrmode`'s fifth number); once it has shown this one and then doesn't (Return to Dashboard, Exit Game, or another game in the theater), ft-screens tags the windows again and shows the panel where it was. If the theater hasn't shown it within 5 s (no ft-dashpatch, or no frame), the panel comes back the same way, so a game is never left untagged with nothing bringing it back (`screens/gstheater.h`). While the theater shows a lent game the tiles hide with the dashboard closed unless `DASH_TILE_STAY_THEATER` is on (off unless set; user, 2026-11-18: "its own separate toggle"), and show when it opens (user, 2026-11-18: "even if I open the dashboard, our applications don't show up"). SteamVR opens the dashboard on the game's tab then, and Steam paints its window only while its own tab shows, so with Steam's window a tile (`STEAM_DASH_PANEL`) that tile stood black in front; ft-screens sends `steamtab` as the dashboard opens, and ft-dashpatch switches a game's tab to Steam's (`TO_STEAM` in `pointer/dashpatch/steampage.py`). The game stays in the theater, and its tab is one click away on SteamVR's bar. A game's app id comes from its window's `STEAM_GAME` or, as gamescope finds it, from the `SteamLaunch AppId=<id>` process its window's `_NET_WM_PID` runs under (Slay the Spire 2's window has no `STEAM_GAME`); a window with neither has no View in Theater row.

`screens/gsforward.h` has the policy (which windows get panels, which panel a popup goes over, keys and buttons as X's) and the X connection on xcb (`screens/gsforward.cpp`). `screens/gslink.h` runs that connection on a thread of its own: X replies wait for the server, so a gamescope that hangs never stalls ft-screens' tick (`screens/tests/gslink-test.cpp` stops an Xvfb to show it). `screens/gsapps.h` has the bookkeeping, `screens/gscontrol.h` what the panels' input and the link's updates do (which window a click focuses, where a key goes, what's let go of when it's turned off), and `screens/vrgsapps.cpp` the overlays. Both it and `screens/vrtiles.cpp` share the panel (`Screen`) and the parts of `screens/vr.cpp` they use through `screens/vrpanel.h`. A click on anything that isn't an app's panel, a Steam panel or the PIN lock included, ends typing to the app. A dialog opened by the window that has the typing takes it, as a window manager would give it; menus and tooltips never do. When a dialog with the typing closes, the window it's for gets it back; when a menu with the typing closes, the window that had it before does. The spike that tried it first (2026-11-16, branch `spike-gamescope-panels`) has the measurements. Limits: X11 windows only (a Wayland client can't be tagged and keeps gamescope's panel); a menu window the app maps again (toolkits keep them) is tagged after it maps, so gamescope's panel can show for a frame; eight apps and eight menus or dialogs at most, for SteamVR's 128 overlays (more keep gamescope's own panel); while tagged, Steam may not treat a game's window as the running game (its overlay and the Steam button); apps that overlap on gamescope's screen are raised as the laser moves onto them, so the X pointer finds the right one. Untested so far: real games, controllers, and someone in a Together room on an app's panel (their pointer doesn't reach it).

### Steam's dashboard window

Steam's big dashboard window isn't gamescope's: it's Steam's own CEF window, named `SteamVR`, on gamescope's first Xwayland (`:0`). Steam forwards it the same way, tagging it with `STEAM_GAMESCOPE_VROVERLAY_TARGET` naming its own overlay, `valve.steam.gamepadui.main`. SteamVR draws dashboard overlays over the room's whatever their depth, so that window covered any tile behind it, and the slot the tiles keep for Steam's menu split them either side of it. With Steam's window on (Display Settings > Visibility & pins > Dashboard tiles, `STEAM_DASH_PANEL=1`; off by default, and `handsetting STEAM_DASH_PANEL 1` switches it live), ft-screens tags Steam's windows with overlays of its own instead, all but the bar and its launcher (`barpopup`). One is a tile: screen 190, the dashboard window, a fixed-size tile anchored to the dashboard the first time (shown with it) and kept as it was after (tile memory key `steam:dashboard`). Screen 191, Steam's left menu (`frame.menu`), is glued to it (above). While the switch is on, the tiles keep no slot for Steam's menu: it's glued to Steam's tile. (Keeping it until Steam's tile was tiled left a slot's gap in the strip: the dashboard opens before Steam's window is tiled.) The rest are followers: the footer, tooltips, the volume level, notifications and Steam's keyboard, each a bare overlay shown while Steam shows its own one, where Steam puts it, and moved with the tile it sits on (`screens/steamplace.h`, `screens/vrsteamfollow.cpp`). The laser on them doesn't go through X: Steam takes its windows' input from its own overlays' laser events and hands it to CEF itself, so the X pointer and XTest on `:0` reach none of them (tried 2026-11-17: the pointer doesn't move, clicks land nowhere). Steam runs CEF with DevTools on 127.0.0.1:8080, each window a page titled as its X window is, so the laser is sent to that page as its mouse with `Input.dispatchMouseEvent` (`screens/steamcdp.h`, the wire in `screens/cdpwire.h`, `screens/tests/cdpwire-test.cpp`): moves, buttons, the wheel, and a move off the page when the laser leaves it, so what it hovered (the menu's labels) hears it go. A click in a Steam text field opens Steam's keyboard, which with Frametop is Full Keyboard: it mounts below the dashboard tile while there is one (`FrametopVr::steam_tile`), not below Steam's own main overlay, which then shows nothing. Off, or ft-screens going, each window gets Steam's overlay back (looked up again then: Steam may have made a new one); a tag of ours left by an ft-screens that crashed goes back the same way the next time it sees the window with the switch on. `screens/steamwin.h` is the policy, `screens/vrsteamwin.cpp` the tiles, on a `gsforward::Role::Steam` link: one that only takes Steam's own display, never clears its tags, and reports each change of a window's target. Each change of a window's target is logged to `screens.log` (`Steam's window: ...`, `Steam popup ...`). If Steam tags a window back itself, it's tagged ours again; after 5 in 10 seconds it's given back and stays Steam's until the switch goes off and on. Keys aren't sent to Steam's pages. Steam's own panels stay shown: while a window is ours its panel has no texture (gamescope forwards a window to one overlay), so it draws nothing. Setting its alpha to 0 made the tile black, because Steam paints the window only while that panel counts as visible (seen in headset captures, 2026-11-17). Shown, though, they still caught the laser: Steam's main panel sits about 1.1 m out, in front of the tiles at 2.7 m, and took the laser meant for the tiles behind it (reported 2026-11-18). So while a window is ours, Steam's overlay for it is shrunk to a ten-thousandth of its width (`screens/steamshrink.h`, `screens/vrsteamhit.cpp`): still shown, so Steam still paints (90 frames a second at 1 mm, 2026-11-18), but nothing there to catch the laser, gaze or hands. Another process may set it (OpenVR's `SetOverlayWidthInMeters` accepts it from ft-screens; `HideOverlay` is denied), Steam doesn't set it back while the dashboard closes and opens, and the pass every second shrinks again any it did. It gets its width back when the window is Steam's again and when ft-screens stops. The shrunk width is the record of the real one (Steam's are 0.3 m and up, so under a millimetre is ours), so when ft-screens starts it lists Steam's overlays with SteamVR's `vrcmd --overlays` and puts back any a crashed one left shrunk, with no file to keep. ft-pointer counts any panel under a millimetre wide as hidden too: it tests Steam's untextured menu against its plane, which takes no width into account, so Frametop's cursor dot still stopped on the shrunk menu (user, 2026-11-18). Each also gets an intersection mask that matches nothing, given back with its width: Steam's main page is a dashboard overlay, and the dashboard sizes it for the laser itself, so shrunk it still took the laser over its full 2.7 m, just over the bar and in front of the tiles (user, 2026-11-18: "the overlays for the invisible game scope window have returned"; on the testbench a click there never reached the tile behind, and with the mask it did). Only those found shrunk get their mask cleared, so a mask Steam sets on its own overlays is left alone. SteamVR also stands its own controls for Steam's page under that page's bottom edge (Show Keyboard, Float in World, View in Theater, More Options): with the page shrunk the edge is at its middle, so the strip floated over the tiles (user, 2026-11-18: "it doesn't look good for it to be visible"), and View in Theater put the page in an invisible theater with no way back. ft-dashpatch now hides that strip with a style rule in SteamVR's dashboard page while ft-screens holds a lease on it (`steamstrip 1` every second; it lapses in 3 s), and reports whether SteamVR's theater shows Steam's page (`pointer/dashpatch/steampage.py`). While it does, Steam's windows are Steam's, as with the switch off, so SteamVR's theater draws them with its own controls and way out; once SteamVR docks the page back they're ours again (the user's pick, 2026-11-18: hand theater to SteamVR rather than make one of Frametop's). Hiding the strip hid SteamVR's View in Theater button too, so Steam's tile has it as a fifth row of its grab bar menu (`screens/vrbarmenu.cpp`): ft-screens sends `steamtheater` to ft-dashpatch, which calls the same `docking.SetInTheater(false)` on Steam's frame that SteamVR's button does. While the theater shows Steam's page the dashboard tiles hide, as the rest of the dashboard does then (user, 2026-11-18: "Hide while theater"), and come back when it docks.

## Approaches we dropped

- WayVR, an existing Wayland desktop for VR. It built and connected to SteamVR on the Frame, but nothing showed in the headset. It has no bindings for the Frame's controllers, and its KDE screen capture needs `xdg-desktop-portal-kde`, which SteamOS doesn't ship.
- gamescope in `PerWindow` mode, for the reasons above. Frametop still supports it as `BACKEND=gamescope`. In that mode SteamVR's dashboard owns the panels, so `ft-layout` floats each one with `vrcmd --dock-overlay` and the pointer helper carries it into place with the virtual controller, hovering first and then sliding at 0.5 m/s, because the dashboard exaggerates fast movements.
- A capture pipeline from a headless KWin through KWin's screencast protocol. It's workable, but ft-screens gets the frames directly with less code.

## Open questions

- A controller button that shows the screens during a game. Games own the controllers, so this needs SteamVR input actions for ft-screens.
- Drawing KWin's cursor on the screens by default. `DESKTOP_CURSOR=1` has KWin draw it itself, for input that isn't the 3D mouse or a laser (Deskflow), but then it shows under the 3D mouse's dot too; ft-screens drawing it only while the 3D mouse and the lasers are away is not built.
- Frame pacing and GPU cost with several busy screens haven't been measured.
- Whether the screen-jump fix (`screens/universefix.h`) catches every screen jump after walking away. It was built from vrserver's logs, not a logged repro of a jump; the tracking watch's lines and the fix's `universe` lines in `~/.local/state/frametop/screens.log` show the next one. A recenter saved per tracking world can also differ from a universe's own standing (the Room Setup origin) when tracking comes back in a new tracking world; screens follow that like any recenter.
- Real standby on a stand, with rendering and tracking paused, not just the backlight off. SteamVR has no call for it, and its activity level follows the proximity sensor.
