# Frametop reference

How each part of Frametop works, where its settings live, and the commands for running parts of it by hand. For why it's built this way, see [design.md](design.md).

## The desktop

From the headset, open Launch a program → Desktop. The installer replaces that launcher entry with Frametop's (`~/.local/share/applications/deckard-nested-desktop.desktop`), and `desktops.sh uninstall` gives the stock single-screen desktop back.

The installer also adds Native Desktop to the same list: a copy of SteamOS's entry for its own desktop (`~/.local/share/applications/native-deckard-nested-desktop.desktop`), skipped when SteamOS has no such entry. The copy is made at install time, so `scripts/update-check.py` warns when SteamOS's entry changes, and `desktops.sh install` refreshes it. In Native Desktop, typing goes to Steam's side, so the input relay doesn't grab keyboards there. While Native Desktop has gamescope's focus, Frametop's keyboard and dictation type there through the relay's virtual keyboard, as the keys of Native Desktop's own layout (`~/.config/kxkbrc`): it reads keys with that layout, not gamescope's, so gamescope's own typing would come out as a US layout's keys. And a Meta tap runs Frametop's Meta action (by default, the Steam menu) as well as opening Plasma's launcher.

From a terminal, on the Frame or from a PC over SSH:

```
desktops.sh install        # the launcher's Desktop entry starts Frametop; Native Desktop is the stock one
desktops.sh uninstall      # back to the stock SteamOS desktop, as Desktop
desktops.sh start | stop | restart | status | log [lines]
desktops.sh streams        # only the remote displays, without the desktop (Frametop Settings, Remote displays)
```

To have the desktop start by itself, turn on Start with SteamVR on the Power tab of Frametop Settings, or run `desktops.sh autostart on`. Both set `AUTOSTART=1` in `~/.config/frametop.conf`. `frametop-autostart.service`, which `desktops.sh install` adds, runs `session/autostart.sh` each time SteamVR starts. The Frame starts SteamVR when it boots, so the setting covers boot too. The script waits for SteamVR's server and compositor, then runs `desktops.sh start`. The desktop quits when SteamVR does, so a SteamVR restart brings it back. If you close the desktop, it stays closed until SteamVR starts again. Its log: `journalctl --user -u frametop-autostart`.

`session/frametop-session.sh` runs the desktop. It starts ft-screens in the `dev` container (log: `~/.local/state/frametop/screens.log`, kept across starts and rotated at 8 MB to `screens.log.1` and `.2`), then KWin and Plasma on the host inside it. Only one Frametop desktop runs at a time. Its check doesn't look for Native Desktop, and running both at once is untested. `desktops.sh start` runs it in its own systemd unit, `frametop-desktop`. It keeps its Plasma config in `~/.config/frametop`, separate from the stock desktop's.

When the VR launcher starts the desktop, it inherits the Steam client's environment. The session script drops the client's runtime from it (`LD_LIBRARY_PATH`, the `STEAM_*` settings, and the Steam overlay's Vulkan layer), so apps in the desktop use the system's libraries, including its video codecs, just as they would after a normal login.

The nested session also starts an AT-SPI accessibility registry through `session/ft-atspi` in Plasma's autostart. It discovers the bus from this session, ignores an inherited host accessibility address, and leaves an existing registry alone. Accessibility errors do not stop the desktop. This supplies the registry infrastructure for apps that expose AT-SPI trees; it does not enable gaze snapping or force Chromium/Electron accessibility. After an approved desktop restart, an AT-SPI-aware app should be visible on the nested bus. See [design.md](design-session.md#nested-accessibility) for native activation, fallback lifecycle, and the isolated test command.

KWin's blur and background contrast effects and its animations are off in this desktop, because KWin draws on the headset's GPU, which SteamVR needs. The session script turns them off once, the first time it starts (it leaves a setting you already have alone, and marks it done in `~/.config/frametop/frametoprc`), so turning them back on sticks. In the Frametop desktop, System Settings → Window Management → Desktop Effects has Blur and Background Contrast, and General Behavior has Animation speed. Or from a terminal, then restart the desktop:

```
kwriteconfig6 --file ~/.config/frametop/kwinrc --group Plugins --key blurEnabled true
kwriteconfig6 --file ~/.config/frametop/kwinrc --group Plugins --key contrastEnabled true
kwriteconfig6 --file ~/.config/frametop/kdeglobals --group KDE --key AnimationDurationFactor 1
```

The desktop's notifications can show outside it, in the Steam session. Plasma there runs on the desktop's own D-Bus, so its popups only appear on the desktop's screens. `session/ft-notifyfwd` (Plasma's autostart; log: `/tmp/frametop-notifyfwd.log`) hands each one to the notification server on the user bus, the one the Steam session's apps use, for example a VR notification server that draws them as panels. Its buttons work: a click there reaches the app as if made in Plasma, and dismissing it there closes it in Plasma. While it forwards, Plasma's own popups are off (do not disturb, held by "frametop"), and Plasma's notification history still has every one. `NOTIFY_FORWARD` in `~/.config/frametop.conf` (or Notifications on the Visibility & pins tab of Frametop Settings) sets it: `auto` (the default) forwards only when the user bus's server isn't SteamOS's own `steam_notif_daemon`, which hands notifications to a Steam client that can't show them on the Frame, so with stock SteamOS nothing changes; `on` forwards to any server, SteamOS's too, where they're lost (it's in the file only; the settings app shows it while it's set); `off` keeps them in the desktop. Restart the desktop after a change. Notifications Flatpak apps send through the notification portal go along too. KDE's inline reply shows as a plain Reply button there; see [design.md](design-session.md#notifications-outside-the-desktop).

Apps that draw their own title bar, like Firefox and Chromium, show the same buttons as KWin's title bars (minimize, maximize, and close unless changed in System Settings → Window Decorations). `session/ft-gtksettings` hands them KWin's button order through the Settings portal; D-Bus starts it in this desktop (log: `/tmp/frametop-gtksettings.log`). Frametop's float button has no GTK counterpart, so those apps use the key or the window menu to float (see [Floating windows](#floating-windows)), or KWin's title bar instead of their own: Use system title bar and borders in Chromium's tab strip menu. Firefox gets KWin's title bar in this desktop by default: the session sets `MOZ_GTK_TITLEBAR_DECORATION=none`, so Firefox's automatic title bar setting picks the system one here, without changing its profile (outside the desktop, it keeps its own). Firefox can't draw its own title bar in the desktop then, whatever Title Bar in its Customize Toolbar says. `FIREFOX_TITLEBAR=firefox` in `~/.config/frametop.conf` gives it back that choice, its own title bar by default (restart the desktop after a change). See [design.md](design-session.md#title-bar-buttons).

Three of the system's autostart programs don't start in this desktop: Discover's update notifier (`org.kde.discover.notifier`), which starts Discover to check for updates, IBus (`ibus`), which can't reach the desktop's apps because KWin's input method is `input/ft-textinput`, and Steam (`steam`), which is already running. The session script puts copies with `Hidden=true` in `~/.config/frametop/autostart` once (marked in `frametoprc`; Steam's was added later and is hidden once on desktops that already had the other two), and skips a name you already have a file for. Delete a copy to start that program again.

Settings are in two files, and Frametop Settings edits both. The screens (resolution, width in metres, scale, curve, which one has the taskbar) and their layout are in `~/.config/frametop-layout.json`. The backend, remote desktop, and pointer settings are in `~/.config/frametop.conf`; `session/frametop.conf.example` lists every key, and [config.md](config.md) says how the file is written (what's quoted, and what happens to a line outside that).

Restarting the desktop closes its windows. Before the unit stops, `session/keep-apps.sh` moves every program started in the desktop into a systemd scope of its own, so background work such as servers, tmux, and builds keeps running. An app that shuts down its own helper processes when its window closes will still lose them; run that kind of work outside the desktop, for example as a systemd user service.

Steam games can run in the desktop too, in place of SteamVR's theater, for portrait screens and rolled floating windows. `steam/ft-ondesktop` goes in a game's Steam launch options (`~/.local/bin/ft-ondesktop %command%`, a link the input relay points at the running install at its start, like `ft-cmd`). Steam starts games for gamescope's Xwayland, and gamescope gives each app's window a theater overlay (`--virtual-connector-strategy PerAppId`, `valve.steam.desktopgame.<app id>`). ft-ondesktop finds the desktop's Plasma shell (the one with `XDG_CONFIG_HOME=~/.config/frametop`), starts the game on its Xwayland instead (`DISPLAY` and `XAUTHORITY`, and its cursor theme), and turns gamescope's Vulkan layer off (`DISABLE_GAMESCOPE_WSI=1`). So gamescope never sees a window for it and makes no theater overlay, and ft-screens, which goes by that overlay, doesn't count it as a theater game: the lasers stay on the screens. It also drops Frametop's virtual pad (045e:028e, `input/vrpad.py`) from SDL's ignore list, so a game Steam started can read the pad in Frametop's gamepad mode, but only while it's the one 045e:028e device in `/proc/bus/input/devices`: a real Xbox 360 pad has the same ids, and Steam Input already gives the game its own copy of that one. Steam's runtime folder, D-Bus, audio, Proton and its container are left as Steam set them. With no desktop running, or its Xwayland socket gone, the game starts unchanged, in the theater. Log: `~/.local/state/frametop/ondesktop.log`.

## ft-screens, the compositor

`screens/compositor.c` is a small wlroots 0.20 compositor that hosts the nested KWin, and `screens/vr.cpp` is its SteamVR side. `screens/build.sh` builds it; the installer runs that for you.

Each KWin window is one screen. ft-screens sets its size with an `xdg_toplevel` configure and KWin resizes the output to match, live. Frames arrive as DMA-BUFs and go to SteamVR through OpenVR's `IVRIPCResourceManagerClient::ImportDmabuf`, with no copy and no size limit.

Every screen is an overlay named `frametop.screen.N` with these controls:

- `.bar` moves the screen. Press and hold it with any laser or with the 3D mouse: after half a second (or as soon as you swing the laser) the screen follows, with a pulse on a controller; the 3D mouse's right-drag tilts. Scrolling while you hold pushes the screen away or pulls it closer, along the line from your head. A quick click on it (let go within half a second, the laser barely moved) or a finger's poke opens its menu instead, and the screen doesn't move (`frametop.barmenu`, one overlay for every panel, `screens/panelmenu.h`). A right click opens the menu's Bar Position page.
- `.resize`, the handle on a corner, sets the size from there, the opposite corner staying put (a screen keeps its aspect; a floating window's panel stretches while you drag, and the window gets that many pixels when you let go; let go, it turns about the kept corner to meet your head as it did when grabbed). It sits on the bottom right, and goes to whichever corner a laser, the gaze or a hand's pinch comes near, brightening as it comes; lit blue while resizing. Screens go down to 15 cm wide.

The bar's menu has what the screen's round buttons used to. Quick tiles sit across its top (Curved and Rotate, plus To Desktop and Close on a floating window; Curved turns blue when on), and a list sits under them:

- **Curved** bends the screen into a cylinder around you, using your current distance as the radius, or makes it flat again.
- **Rotate**, held, rolls the screen as you move the laser sideways, like a knob held at the middle of its top edge with a top bar, or of its bottom edge with any other, wherever on the row you hold it. The knob stays on its side of the centre, so drifting up or down as you sweep doesn't turn it back, and one hold turns it up to about 90° each way. It snaps level within 2.5°. A click (or a finger's tap) levels it.
- **Placement** shows where the panel lives (In the Room, Keep in View, On Dashboard, or On a Wrist) and opens a page to change it: **In the Room** leaves it where it is, **Keep in View** pins it to your head (see below), and **On Dashboard** anchors it to the SteamVR dashboard. The one it is has a check. **Stay Shown** (while anchored) keeps it shown with the dashboard closed.
- **To Desktop** and **Close**, tiles on a floating window. **View in Theater**, on Steam's tile and a Steam game's panel.
- **Bar Position** puts the bar on the bottom, top, left or right edge.
- **Reset Layout…** is the quick reset, like Meta+Shift+R (`ft-layout reset`). It asks first (Reset or Cancel on the question beside the bar), then shows a head-following three-second countdown, then puts the screens and remote displays back in their layout around where you are now, without reopening the profile's apps or changing windows, fullscreen, hidden screens, sizes, or streams. A panel pinned to the head with Keep in View goes back in the room (unless the profile saved it pinned); one on a wrist stays. Opening the profile (frunner, or Open profile in Frametop Settings) restores all of it.
- **Move All Screens** moves the whole layout. Hold it with any laser or with the 3D mouse, and its screen is carried as by its bar, while every other screen, remote display and floating window in the room goes with it in one piece: the layout turns about you as the screen goes round you, rises and sinks with it, and comes nearer or goes away with it. Nothing in it tilts, however your hand turns the screen you carry. The panels it moves show a fuchsia border meanwhile. Panels pinned to your head or a wrist stay on their pins, a panel another laser or a hand holds stays with that, and hidden screens and stopped remote displays keep their place in the layout. It moves nothing while the screen you carry is nearly straight above or below you. Let go and the layout stays there; the quick reset puts it back around you. Remote displays have it too; floating windows don't. The rules are in `screens/layoutgrab.h`. A hand's tap doesn't do it: it's a laser's hold.

A panel's controls are just the bar and the resize corner: a pooled set of two overlays (`screens/chromepool.h`), lent to the panels a laser, the 3D mouse or a hand comes near. They're sized from both the screen's width and its distance from you, follow the surface of a curved screen, and stay invisible until a laser or the 3D mouse's cursor lands on one or comes near. While invisible they're still there, fully transparent, so SteamVR's laser can find them. They're translucent until a laser is on them, like SteamVR's own window controls.

To pin a screen to a wrist, carry it by its bar and sweep the laser across your other controller. A ring around that controller marks the target, and a dot shows where the laser passes. Crossing the ring arms the pin, and the ring and bar turn blue; crossing it again disarms it. When you let go while armed, the screen rides on that controller at the size, distance, and angle it had, so you can arm the pin first and then turn the screen the way you want. Grab a pinned screen's bar to adjust it; it goes back to the same wrist when you let go unless you disarm it. A pinned screen shows only while you're looking at its front, within the wrist angle, and fades out over the last 10°.

To pin a screen to your head, like a HUD, pick Keep in View under Placement in its bar's menu (pick In the Room there to leave the screen in the room where it is then), or set it to On your head on the Visibility & pins tab of Frametop Settings (or `ft-layout pin N head`). Remote displays have it too. A layout reset ends a pin Keep in View made: the screens go back as the profile has them, pinned only if it saved them pinned. It rides on the headset where it is at that moment, so place it first, and it shows whenever the screens do. Grab its bar to move it; it goes back on your head where you let go. Sweeping across a wrist ring while you carry it moves it to that wrist, and sweeping across again leaves it in the room. The 3D mouse's dot stays in the room, so a head-pinned screen moves away from it when you turn your head, unless head follow is on. Visibility & pins > Head pins picks how a head-pinned screen follows you (`SCREEN_PIN_LEVEL`). Ride on the headset (0, the default) moves it with every turn, look and tilt. Pin only follows horizontal movement (1) makes it follow you turning and walking but stay level and at its height: looking up or down, tilting your head, or crouching leaves it where it is. Pin follows walking only, not turning (2) moves it with you as you walk, at its height and facing the same way in the room, like a ball round you: turn your head to see the screens beside or behind you. Switching it changes screens already on your head where they are.

To keep a panel on the SteamVR dashboard, pick On Dashboard under Placement in its bar's menu (with a laser, or a finger's tap): a screen, a floating window, a remote display, or an app started from the dashboard. Anchored panels stand on a desk round you like monitors of their own sizes (each at its natural size, so text is the same size on all of them), in front of you each time the dashboard opens, either side of Steam's menu when it's in front, and move with it. Once the desk is as wide as Desk width (120 degrees), a new panel goes on top of the lowest column. With Steam's window on (Visibility & pins > Dashboard tiles, `STEAM_DASH_PANEL`, off by default), Steam's own dashboard page is a tile like the rest, and Steam's menu is glued to its left edge: only the part Steam draws shows, and it moves and tiles with it. Its grab bar menu has View in Theater for Steam's page; SteamVR's theater shows it with its own controls, and it's a tile again once docked. They show only while the dashboard is open, unless Stay visible is on (Visibility & pins > Dashboard tiles) or you switch Stay Shown in its bar's menu for that panel. With the pointer or your gaze on one (Look to focus, under Dashboard tiles: on unless `DASH_TILE_LOOK=0`), `Meta+Shift+Left` and `Meta+Shift+Right` move it between columns, `Meta+Shift+Up` and `Meta+Shift+Down` within its column (alone in its column, Up lifts it with a neighbour in under it and Down hangs it under the next column), and `Meta+Ctrl+Right` or `Up` make it bigger, `Meta+Ctrl+Left` or `Down` smaller (about 10% a press, a quarter to six times its natural size). `Meta+/` lists every key combination ([Frunner](#frunner)). Drag a tile to reorder; pull it well away and it stays anchored where you let go. Each app, screen and remote display remembers whether it was anchored. On `@ft_screens`: `anchor N|focused on|off|toggle`, `stay N|focused on|off|toggle`, `tile left|right|up|down|wider|narrower|taller|shorter` (the focused tile), `tiles` (each anchored panel's state, by column and row), `tiles clear`, `tiles gaps` (the smallest gap between tiles and either side of Steam's slot, from the panels as SteamVR shows them, then each one's span), and `tiles set N STATE; N STATE...` (then `tiles add N STATE...` within 5 seconds for more of the same set, after its columns; a later add goes after every tile). Display Settings sends the wall's settings (the desk line, panel size, desk width and distance) as `handsetting DASH_TILE_*` ([design.md](design.md#dashboard-tiles)).

With Dashboard apps on (Display Settings, `GSAPP_PANELS`, on by default), a flatscreen X11 app you start from the SteamVR dashboard opens as a Frametop panel instead of Steam's, anchored and staying visible the first time. Click it to type into it. Its menus open over it. Apps that ignore synthetic keys (xterm, some games) don't take typing, and Wayland apps keep Steam's panel. GTK3 apps type once their Steam launch options are `GDK_CORE_DEVICE_EVENTS=1 %command%` ([design.md](design.md#gamescope-apps)).

The Visibility & pins tab of Frametop Settings decides when the screens show:

- Always. Meta+Shift+H (the input relay's `screens_toggle`, rebindable in Frametop Settings), the Hide/Show Screens menu entry, or a mapped mouse or controller button hides them, and shows them again.
- Only while the SteamVR dashboard is open.
- While you look at a chosen controller (the wrist gesture).
- Only after you show them with the hotkey.

In the last three modes the hotkey shows the screens anyway. A screen can also be hidden on its own (Screens shown on the same tab, or `ft-layout hide N`): it stays hidden whatever the mode or the hotkey says, until it's shown again there. Windows on it stay put, and a new window that would open on it floats instead (ft-floatd). Profiles use this to show only some screens. Two more settings on the same tab cover VR games, which ft-screens detects as SteamVR scene apps:

- During VR games, the Always mode hides the screens unless the dashboard is open (the default), or leaves them up.
- Controllers on the screens. Visible screens can keep SteamVR's laser mouse on, so controllers work them with the dashboard closed, but that also takes the controllers away from a game. By default this is off while a VR game runs, and the 3D mouse or the dashboard works the screens. Pointing a controller at a screen, a floating window, or the keyboard still turns its laser on, like SteamVR's own floating windows, and pointing away gives the game the controllers back. The other choices are always on, or only with the dashboard open, which also suits flatscreen games since they aren't scene apps.

Input from the lasers reaches KWin through ft-screens' own seat. Keys come from the input relay: from pass-through keyboards, a keyboard's media keys (its Consumer Control node), and any key a pointer device passes through. A mouse button passed through as a key in pointer mode (a side button for Back) goes to the screen the pointer is on instead, wherever typing goes, and only while the pointer is on a screen that shows and Frametop isn't paused. Its release always goes through, and ft-screens releases it itself when the pointer leaves the screens, its screen hides, or Frametop pauses (`screens/tests/relay-buttons-test.c`, in `just test-c`, checks this offline). A key's release always reaches KWin too: when the screen with keyboard focus closes, focus moves to one that's left and the keys held come up there, and a release with no screen focused waits for the next focus (`screens/held-keys.h`). `keys` on `@ft_screens` says what's held, and `keys release` (the relay's Ctrl+Alt+Shift+Esc) lets go of every key. Typing follows your last click: after a click on a screen it goes to the desktop, even with the SteamVR dashboard open, and after a mouse click on any other panel (the dashboard, Steam, an app like Spotify) it goes there instead. While it goes to the desktop, the relay grabs pass-through keyboards so gamescope, which reads every keyboard itself, doesn't type them into the Steam app too. A program that watches every keyboard for a hotkey loses a grabbed one; bind its key as a key combination with a command instead (Frametop Settings, Keyboard). Frametop Voice types its text through the relay the same way, so it lands where typing goes. Hidden screens don't take typing. In a Frametop Together room, someone you gave a panel to shares that seat with you by turns, and a window of your PC that you gave them takes their input through its own stream (`peer` on `@ft_screens`, `screens/peerinput.h`; [together/README.md](../together/README.md), "To the desktop").

Frametop's keyboard opens by itself when a text field on the desktop gets focus, and stays open until its X, a layout reset, or a mapped button closes it (or, with Keep it open off in Frametop Settings, until the text field loses focus). KWin starts `input/ft-textinput` as the desktop's input method, and KWin activates it whenever the focused app turns on text input for a field. It tells the relay (`textfield 1` or `0`), the relay decides by the Keyboard setting in Frametop Settings, and ft-screens opens the keyboard (`vrkeyboard show`, `hide`, or `toggle` from a mapped button). Its keys reach the focused screen as key presses, so it works in every app, but only apps that use Wayland text input (Qt, GTK, Firefox) open it by themselves; Chromium, Electron and X11 apps need the button. The session drops the `QT_IM_MODULE=xim` and `GTK_IM_MODULE=xim` that the gamescope session sets, or Qt and GTK apps wouldn't use Wayland text input either.

Frametop's keyboard is Full Keyboard for Steam Frame, by TaiKeid (`keyboard/`, MIT; [keyboard/FRAMETOP.md](../keyboard/FRAMETOP.md)), when it runs: the user service `frametop-keyboard.service` starts it with SteamVR (`keyboard/host/ft-kbhost`, which starts the release `keyboard/build.sh` downloaded, in hosted mode), and restarts it if it crashes. Each build takes Full Keyboard's newest release (`FULLKB_VERSION=x.y.z keyboard/build.sh` an exact one). It has full layouts, languages and input methods, themes, and replaces Steam's own keyboard in Steam's text fields, by the same Keyboard setting as the desktop's. ft-screens passes its `vrkeyboard` commands to it through the input relay. It's the only on-screen keyboard: while it isn't running (no word from it for 3 seconds), a text field or the keyboard button opens nothing, and ft-screens' log says `keyboard not opened (...): Full Keyboard isn't running`. A keyboard you plug in, dictation, and Steam's own keyboard in the dashboard still work then. (ft-screens' own key panel, a US layout only, was the fallback until the 2026-10-31 cleanup removed it.) It shows over the screens with the dashboard closed while Frametop asked for it, and in the dashboard as always. Its typing goes where typing goes: on the desktop, the relay types it on ft-screens' seat (text and Ctrl/Alt/Super+letter shortcuts through the desktop's layout, whatever Full Keyboard's language; other keys by their place; text the desktop's layout has no key for, like Chinese or Japanese, isn't typed there yet), and Steam and games get it through gamescope as before. A click on its panel leaves typing where it was. Poke a key with a fingertip as on Frametop's screens, with no laser, or click it with a laser. Its settings are in `~/.config/frametop-keyboard`.

```
keyboard/run.sh status | restart | log [lines] | install | uninstall
keyboard/build.sh                           # its newest release, in keyboard/build/release
```

To run a Full Keyboard of your own instead (its own install, or one from Nix, started by its `framekeyboard-autostart.service`), install with `./install.sh --no-keyboard` (or `get.sh --no-keyboard`, which passes it on, with or without `--release`). Frametop's copy asks every other `framekeyboard` to quit when it starts, so it's left out: the install doesn't build or install it, removes one an install before left (and starts yours again if that one was running in its place), and doesn't change yours. Without the option, an install that finds `framekeyboard-autostart.service` enabled asks which one to use (Frametop's, by default and with `--yes`). Your own copy types as it always has, but Frametop's screens can't open it for text fields or the keyboard button: that takes Frametop's hosted copy.

KWin's nested backend doesn't undo a screen's scale on pointer input, so ft-screens divides panel positions (in pixels) by it. `ft-layout` sends it each screen's scale as KWin reports it (`scale N s`) whenever it applies scales: at desktop start and from Frametop Settings. A scale changed only in Plasma's own display settings is put back to the Frametop layout's the next time `ft-layout` runs.

Each screen draws at a frame rate for how much of it you see. KWin draws a screen only after ft-screens gives it a frame callback, and its apps wait for theirs, so the rate of callbacks is the screen's frame rate, for KWin and the apps on it alike. A screen is focused while you look at it (within 12 degrees of where your head points), while a laser or the mouse is on it or was in the last 1.5 seconds, while it's carried, and while you type on it; it gets every display frame. The rest of what you can see (within 60 degrees) gets 15 frames a second, and a hidden screen, one behind you, and everything while paused get one a second. A level goes up at once and comes down after a moment (1.5 s from focused, 0.5 s from in view). A video, or anything moving over a large part of a screen (6% or more of it, redrawn on 8 commits in a row, 10 or more a second), keeps every frame while in view. A floating window is a screen of its own here. Nothing that stands still costs anything at any rate: KWin sends a frame only when something on the screen changed. `rates F V H` sets the three rates in Hz (0: every display frame; default `0 15 1`, also `ft-screens --rates 0,15,1`), and `rates?` shows them, the display's rate, and for each screen its level, its milliseconds between frames, and whether it counts as a video. `watch S` gives every screen full rate for S seconds: remote desktop renews it while a VNC client is connected, since a viewer sees what KWin draws. The ticks (SteamVR events and the callbacks) come once per display frame, 1 ms after the vsync (`phase ms` changes that, for tuning), in step with the display rather than on a timer that drifted through the frame.

`spin` is the lazy susan. By default it brings panels to a front slot at reading distance and leaves the rest where they are: `next` and `prev` bring the next one round on the right or left (the one in the slot goes home), and `to N` brings panel N. With `SCREEN_SPIN_BRING=0` in `~/.config/frametop.conf` it turns every panel in the room about your head instead: `next` and `prev` bring the next one on the right or left to straight ahead, and `to N` turns the short way to panel N. A brought screen comes `SCREEN_SPIN_DISTANCE` ahead (1 m; 0.9 to 3; Frametop Settings, Hands, Gestures, which sends `spindistance M`). Push or pull one in the slot (the wheel while carrying it, or a carry straight out or in) and it comes back that far and as big in view each time, never nearer than frunner's search allows, until a layout reset; a hand's push still sends it home. Either way, a number of degrees turns the room that far. Typing goes to the panel that ends up in front. `front N` gives panel N the typing where it is, as a spin to it would. `frunner on`, renewed every second, gives frunner's search the typing, and `frunner off` gives it back ([Frunner](#frunner)).

`conceal` and `reveal` hide and show one screen on its own (`ft-layout hide` and `show` send them), and `concealed` lists those screens. `pause on` (from the input relay, when Frametop pauses for a VR game) hides every screen and floating window whatever else says, and slows the desktop down; `pause off` undoes it. `cutouts` turns the hand cutouts on and off (`ft-handsctl cutouts`), and sets their matte, its margin and the per-distance correction (hands/README.md, "Hand cutouts and near input"); they cut only with Room View on, detected or forced (`cutouts roomview`, hands/README.md "Rendered hands"). `wallpaper on` reads the stereo wallpaper's pictures again and shows them, `wallpaper off` stops (Frametop Settings sends both; see [Stereo wallpaper](reference-features.md#stereo-wallpaper-experimental)). `hands` is the pointer helper's word on hand input (each side `hand`, `controller` or `off`, and whether it's allowed now); `handinput` turns near input on (following that word), off, or on without it, and `handinput state` reports what each hand is doing, its counts (presses, one-frame presses, pinch clicks, grabs by card and fist, poke attempts and those refused, crossings off the content, presses at the edge, flicks and throws, holds through tracking loss, second hands joining a held panel, pinches that waited to become fists, buttons pinched) and what held presses back; each press, release, refused poke and grab also goes to ft-screens' log as a `hands:` line. `palmmenu` turns the palm menu (a bare hand palm up, pinch: the Steam menu) on and off, and `palmmenu state` reports it. `grabthat` turns "grab that" (an open hand held out to a panel farther than arm's reach, then a fist pulled back: it comes to arm's reach) on and off, and `grabthat state` reports each hand's state, its counts and the panels that came. The last line is ft-floatd's, for floating windows: N is a floating window's panel, numbered on from the screens, one per spare output. `float` gives the window's rectangle in its output, metres per pixel, and the title bar's height, and shows the panel; `unfloat` hides it. `pose` places it (a 3x4 matrix, standing universe), `sub` shows popup or dialog k over it, `minimized` hides it while its window is minimized, `carry` moves it with the laser that pressed the window's own title bar (`carry toggle`, from the input relay's `carry_toggle`, carries the panel under the 3D mouse instead, any panel (off every panel: the one nearest straight ahead of the eyes), by its centre (the helper's `aimat x y z` puts the cursor there), until a click or Enter (not while a button holds a title-bar or torn carry, nor a pinned panel; `pause on` ends it): the click goes nowhere else, a panel's controls included, another `carry toggle` meanwhile turns carry-all on or off (the other unpinned panels, with fuchsia borders, and the cursor follow the head: the helper's `follow carry on x y z`, head follow with no leash, the cursor kept on the point held as its origin goes to the eye), Ctrl held moves it in its own plane, Alt held turns it about its centre, keeping its angle in the room (the pointer helper's `carry turn on` sends the mouse's moves as `carryturn <dyaw> <dpitch>` instead of moving the cursor), Space levels its roll about its centre on its release (twice: it faces the head too; in carry-all, every panel that follows the head as well; held 0.3 s instead, it and the cursor follow the head, as in carry-all but alone, till Space comes up, the grid fuchsia then and in carry-all), Tab and Shift+Tab move the carry to the next panel right or left round the head (in carry-all, of those within 50 degrees of straight ahead), the wheel pushes it or pulls it in, whatever panel the ray is on, Esc or Backspace ends the carry and puts the panels it moved back as they were; `carry take N`, from ft-floatd when a window goes from the desktop to floating with `carry_on_float` on (Frametop Settings' rules, off by default; not a torn-off one), starts the same carry of panel N as soon as it shows, an aqua border round it pulses every 5 s and fades with a last pulse when it's let go, and a faint grid round it shows the sphere it moves on (Ctrl: its plane; Alt: red, green and blue rings round its axes); Ctrl, Alt, Shift, Tab, Space, Enter, Esc and Backspace pressed meanwhile don't reach the desktop), `moving` is KWin's word that a window on a screen is being moved by its title bar (a pull on the wheel then tears it off), `torn` carries a torn-off window on with the laser that tore it, held at gx, gy in its pixels, and `hold` keeps its picture and crop for up to ms (0 to 2000; 0 ends it) while ft-floatd changes the window's scale or size: new frames wait, a `float` meanwhile goes up with the first frame 60 ms after it, so the in-between frames don't show.

## Input relay

SteamVR opens input devices only when it starts. A Bluetooth mouse that sleeps and reconnects gets new device nodes, SteamVR keeps reading the dead ones, and the mouse stops working until SteamVR restarts. `input/input-relay.py` avoids this. It creates two virtual devices, `frametop virtual mouse` and `frametop virtual keyboard`, through `/dev/uinput` before SteamVR starts. It then grabs USB and Bluetooth mice and keyboards as they come and go and forwards their events, so SteamVR only ever sees the virtual devices, which never go away.

It runs as the user service `frametop-input-relay.service`, ordered before `steamvr.service`.

The relay also owns the volume keys, on every device that has them, the headset's buttons included. It changes the volume itself (`wpctl`, 5% a step, repeating while held), and nothing else sees a volume key, gamescope and SteamVR included: on devices with a keymap (the headset's `gpio-keys`, USB and Bluetooth keyboards) it remaps just the volume entries to unused codes (`KEY_MACRO29`, `KEY_MACRO30`), so the headset's click button and the other keys still work, and it grabs `pmic_resin`, which has only volume down. The keymaps go back when the relay stops. With `--no-grab` it leaves the volume keys alone.

```
desktops.sh relay install     # enable it (starts with the next reboot or SteamVR start)
desktops.sh relay status | log | uninstall
input/input-relay.py --no-grab   # try it without taking devices from SteamVR
input/test/keys-test.py          # key combinations, modifier taps, dictation's and Full Keyboard's typing, and what reaches the desktop, against fake devices (safe next to the live relay)
input/test/roles-test.py         # each node's role, Keyboard + 3D pointer included, offline
input/test/scroll-test.py        # the wheel through the virtual joystick: a step per notch, fast notches added up and capped, offline
input/test/magicmouse-test.py    # Magic Mouse 2 surface-to-wheel decode, offline
input/test/gamescope-focus-test.py # Native Desktop's gamescope focus, against a fake libxcb
input/test/kb-shortcuts-test.py   # Full Keyboard's shortcut letters on other layouts, offline
input/rules-migrate.py           # one-time changes to a key_bindings list of your own (install and update run it)
input/test/rules-migrate-test.py # those changes, on files in a temporary folder
steam/ft-steam menu              # what Open Steam menu does; ft-steam check: Steam's UI still has the calls
```

The first time, the relay has to start before SteamVR, so reboot or restart SteamVR after installing it. After that it's safe to restart on its own: systemd keeps the virtual devices open in its file descriptor store (`FileDescriptorStorePreserve=yes`), so SteamVR keeps the same devices.

## The 3D mouse

A mouse drives SteamVR the way a controller's laser does, but shows up as a small dot anchored in the room. It snaps onto panels and works on the dashboard, Steam, overlays, and the desktop. Three pieces make it work:

- The input relay, in pointer mode (`POINTER=1`), sends mouse motion, clicks, and scrolling to the helper. A deliberate movement or a click wakes the pointer, and 30 seconds without mouse input releases it.
- The helper, `pointer/helper/ft-pointer`, runs in the `dev` container as `frametop-pointer.service` and starts with SteamVR. It keeps the cursor, tests it against every visible overlay, draws the dot, and sends the driver an exact pose.
- The driver, `pointer/driver/` (`ft_pointer`), is loaded by SteamVR. It's an invisible virtual controller whose laser follows the cursor. It takes the treadmill role, no hand, so the real controllers keep theirs and one can be used beside it (`POINTER_ROLE` and the driver's `role` setting; see docs/design.md, "Treadmill role").
- The dashboard patch, `pointer/dashpatch/` (`frametop-dashpatch.service`, starts with SteamVR), lets that treadmill move SteamVR's own windows by their grab bars, which SteamVR allows only for the head or a hand. It goes into SteamVR's dashboard page through the dashboard's debugger, which the installer turns on at 127.0.0.1:8089 (`VRWebHelper/DebuggerEnabled`; the uninstaller turns it off). `pointer/dashpatch/run.sh status` shows whether it's in. It also reads two things only that page knows and tells ft-screens (`steamvrmode ...`): whether SteamVR's controllers are in Gamepad mode (Enter Gamepad Mode in the Steam menu), which Steam game shows in a theater window, and whether SteamVR's theater shows Steam's own page (ft-screens then gives Steam's windows back to Steam until it's docked again). While ft-screens has Steam's window as a tile it also keeps SteamVR's controls under Steam's shrunk page hidden (`steamstrip` on @ft_dashpatch, `pointer/dashpatch/steampage.py`), and asks SteamVR to show Steam's page in its theater when the View in Theater row of Steam's tile's grab bar menu is clicked (`steamtheater`); the dashboard tiles hide while it's there. A theater game counts as a game for `controllers outside_games`, and in Gamepad mode no panel turns SteamVR's laser on, so pointing at a screen doesn't take the pad from the game; the grips bring the laser back. Gamepad mode with a Frametop screen or the Full Keyboard last clicked (on top of SteamVR's focus stack) counts as laser mode, since SteamVR switches to Gamepad mode by itself when the Steam menu closes and the pad can't drive a screen.

Gamepad mode works for Frametop panels too, through SteamVR's own. With the Steam menu open, ft-screens shows an "Enter Gamepad Mode" pill above the panel typing goes to (a desktop screen, a floating window, or a remote display). Clicking it puts SteamVR's controllers in Gamepad mode for that panel; the grips bring the laser back, as in a game. A Steam game's panel has no pill: its View in Theater button gives the game SteamVR's theater, where Steam Input sends it the pad. SteamVR gives its Gamepad mode only to a dashboard overlay's owner, so ft-screens owns one, `frametop.gamepad` (no tab, and overlay flag `1 << 4`, which hands its page ft-screens' pid for VR input). The pill's click goes to ft-dashpatch (`gamepad` on `@ft_dashpatch`, from the same user only; `pointer/dashpatch/gamepadmode.py`). Up to SteamVR 2.18 it pushes SteamVR's input focus onto that overlay's page and closes the Steam menu once the focus took, as SteamVR's own pill does for a tab that isn't in front. SteamOS 0.4.5's SteamVR keeps the focus on the panel clicked last (issue 105), so when the push hasn't taken within 0.5 s it closes the menu anyway and arms the Gamepad mode that follows: ft-dashpatch counts it as Frametop's until it ends, or for 15 s if it never starts. SteamVR 2.19 (SteamOS 0.5) ignores that push for a tab that isn't showing (the menu closed and the controllers stayed lasers, 2026-11-18), so there it switches the dashboard to `frametop.gamepad`'s tab and dims it (SteamVR's diminished dashboard, what its own pill does for the tab in front). The tab shows a card naming the panel with the pad and how to leave, and that panel stays shown while the rest of the dashboard is dimmed. If SteamVR doesn't give the page the focus within 2 s, the dashboard goes back to the tab it showed and stays open; when the dimmed mode ends it goes back to that tab too. ft-dashpatch then tells ft-screens the Gamepad mode is Frametop's (`steamvrmode 1 <app> 1`: SteamVR's VR input goes to ft-screens' pid, with no Steam app's input in the way, or in 2.19 with `frametop.gamepad`'s page on top of the focus stack), and ft-screens tells the input relay `gamepad desktop|remote` every second (`gamepad off` as it ends). SteamVR sends an overlay no input in Gamepad mode, so the relay's controller reader (`input/game_pause.py`) reads the buttons, sticks and triggers raw from vrserver's web socket. A desktop panel gets them as a virtual Xbox 360 pad on uinput (`frametop virtual gamepad`, kept in the relay's fd store), and a remote display as a Moonlight Xbox controller on the host (`pad ...` through ft-screens to its ft-stream). The pad lets go while a dashboard opened during gamepad mode is open (one the pointer helper still calls open as it starts doesn't count: 0.4.5's says so after the pill closed it), ends when Frametop pauses or a VR game starts, and buttons held as it starts wait for their release (`input/vrpad.py`). Steam also sees the virtual pad, as a controller; it gets no input from SteamVR while the pad is Frametop's.

Whichever device you used last wins. Picking up a controller hands the laser back at once, and moving the mouse takes it again. With hand interaction (`POINTER_HANDS=1`), this goes per hand: a controller used recently wins its hand, and the other hand can stay bare. When the headset comes off, the pointer lets go, so the displays can sleep, and it stays off until you're wearing the headset again.

To move a floating panel, left-drag its grab bar. The scroll wheel pushes and pulls it while you drag. Hold the right button while dragging and move the mouse to tilt the panel around the grab point; the right press isn't sent as a click. The tilt stays for the rest of the drag, and releasing the left button drops the panel as it is. A mapped Toggle dashboard button wakes the pointer if needed and holds the virtual system button for 0.12 s, because SteamVR ignores a press and release in the same instant. Open Steam menu / close dashboard (`steam_menu`) needs no pointer: `steam/ft-steam menu` asks Steam's UI, over its debugging port (`steam/steamui.py`), to show its dashboard overlay and focus the Steam frame's menu, or to hide the dashboard if it's up.

```
pointer/driver/build.sh && pointer/driver/install.sh install   # then restart SteamVR
pointer/helper/build.sh && pointer/helper/run.sh install
pointer/helper/run.sh status | log | restart
pointer/driver/install.sh probe     # devices, hand roles, activity, charging, who owns the dashboard pointer
pointer/probe/build.sh              # probes: vrprobe, lasertest (who has the laser), ctlnoise (controller noise)
```

The pointer settings are in `~/.config/frametop.conf`: `POINTER_SENSITIVITY`, `POINTER_IDLE`, `POINTER_WAKE_COUNTS`, `POINTER_CONTROLLER_PICKUP`, `POINTER_DISTANCE`, `POINTER_CURSOR_DEG`, `POINTER_ORIGIN_FRACTION`, `POINTER_ORIGIN_MARGIN`, `POINTER_SCENE_RADIUS`, `POINTER_EDGE_REACH`, `POINTER_LASER_WIDTH`, `POINTER_IGNORE`, the head follow settings `POINTER_FOLLOW`, `POINTER_LEASH_DEG`, `POINTER_LEASH_DELAY`, `POINTER_LEASH_RETURN`, and `POINTER_FOLLOW_REACH`, and the gaze mode settings `POINTER_GAZE`, `POINTER_GAZE_RETAKE`, `POINTER_GAZE_NUDGE_MAX`, `POINTER_GAZE_HOLD`, `POINTER_GAZE_CONTROL_HOLD`, `POINTER_GAZE_DOT`, `POINTER_GAZE_SHOW`, `POINTER_GAZE_MOUSE`, `POINTER_GAZE_MOUSE_MOVE`, and the keyboard clicks' `POINTER_HEAD_DEADZONE` and `POINTER_KEY_TAP`, and the gaze service's `GAZE_TRACKER` (`auto`, the default: our own eye tracker when it's installed, else SteamVR's; or `own` or `steam`), `GAZE_EYE` (the eye bias), `GAZE_FIT_WATCH` (the put-on check and the slip note, off by default: [gaze/README.md](../gaze/README.md), "Headset fit"), and `GAZE_FUSION` (our tracker's gaze mixed with SteamVR's, off by default: [gaze/README.md](../gaze/README.md), "Gaze pointer"), and our eye tracker's `EYES_SIZE_GUARD` (`both`, the default, `long`, or `off`: [gaze/README.md](../gaze/README.md), "Our own eye tracker"). The example config explains each. Frametop Settings changes them live; after editing the file by hand, restart the relay or the helper (the gaze service reads its four again when the file changes; ft-eyes reads `EYES_SIZE_GUARD` when it starts).

## Limits

- A controller button can't show hidden screens; a mapped mouse or keyboard button can.
- KWin's cursor isn't drawn on the screens, because KWin draws it as a host cursor, which ft-screens doesn't render. The 3D mouse's dot and SteamVR's laser dot show where you're pointing. Input that reaches KWin without them moves a cursor you can't see: Deskflow's (it comes through libei) or a remote desktop's. `DESKTOP_CURSOR=1` in `~/.config/frametop.conf` has KWin draw the cursor into the screens' pictures itself (`KWIN_FORCE_SW_CURSOR`, after a desktop restart); it then also shows under the 3D mouse's dot.
- The old gamescope backend (`BACKEND=gamescope`) still works, but it gives every screen the same resolution, at most 1920×1080 pixels' worth, and arranging screens borrows the pointer for a few seconds.
